# kdbg

A minimal Linux x86_64 debugger written in C, based on `ptrace(2)`.
This is a learning project: the goal is to understand how debuggers like GDB actually work.

## Build

Requires [Capstone](https://www.capstone-engine.org/) for disassembly:

```sh
sudo apt install build-essential libcapstone-dev
```

```sh
make
./kdbg ./test/hello
```

> **Note:** addresses in the examples below come from one specific build. Your compiler may lay out the binary differently (e.g. with or without `endbr64`), so always check them with `nm`. A breakpoint placed in the middle of an instruction corrupts it and usually crashes the program.

## Usage

```sh
./kdbg <program> [args...]   # launch a program under the debugger
./kdbg -p <pid>              # attach to a running process
```

Press **Ctrl+C** while the target is running to stop it and get back to the prompt.

## Commands

| Command | Description |
|---|---|
| `r`, `regs` | show registers |
| `s`, `step` | execute a single instruction |
| `n`, `next` | step over calls |
| `f`, `finish` | run until the current function returns (prints `rax`) |
| `c`, `continue` | resume execution |
| `b <loc>` | set a breakpoint (e.g. `b main`, `b 0x401126`) |
| `bl` | list breakpoints and watchpoints |
| `d <n>` | delete breakpoint `n` |
| `watch <loc> [len]` | hardware watchpoint: stop when `loc` is written (`len` = 1, 2, 4, 8) |
| `awatch <loc> [len]` | stop when `loc` is read or written |
| `unwatch <n>` | delete watchpoint `n` |
| `x <loc> [n]` | hexdump `n` bytes of memory (default 32) |
| `set <loc> <value>` | write a 64-bit value at `loc` |
| `dis [loc] [n]` | disassemble `n` instructions (default: 8 from `rip`) |
| `strace [name]` | trace syscalls; with a name, stop after the next call of that syscall |
| `bt` | backtrace (call stack) |
| `syms` | list function symbols |
| `h`, `help` | show help |
| `q`, `quit` | kill the target (or detach, with `-p`) and exit |

`<loc>` is either an address (`0x401126`) or a symbol name (`show`, `secret`).

## How it works (M1)

1. `fork()` → the child calls `ptrace(PTRACE_TRACEME)` and then `execvp()`.
2. The kernel stops the child with `SIGTRAP` right after `execve`.
3. The parent (the debugger) controls it with `PTRACE_GETREGS`, `PTRACE_SINGLESTEP`, `PTRACE_CONT` and `waitpid()`.
4. ASLR is disabled in the child (`personality(ADDR_NO_RANDOMIZE)`) so addresses stay stable between runs.

## How it works (M2)

1. `b <addr>` reads the 8-byte word at `addr` (`PTRACE_PEEKDATA`), saves its lowest byte and replaces it with `0xCC` (`int3`) using `PTRACE_POKEDATA`.
2. When the CPU executes `int3`, the kernel stops the tracee with `SIGTRAP`; `rip` now points to `addr + 1`.
3. The debugger restores the original byte and sets `rip = addr` (`PTRACE_SETREGS`).
4. On the next `step`/`continue` it single-steps the original instruction and writes `0xCC` back, so the breakpoint stays active.

Try it:

```sh
nm test/loop | grep -w add    # find the address of add()
./kdbg ./test/loop
kdbg> b 0x401136
kdbg> c                       # hit 3 times, once per loop iteration
```

## How it works (M3)

- `x` reads memory word by word with `PTRACE_PEEKDATA` and prints a hexdump (hex + ASCII). Bytes covered by an active breakpoint are shown with their original value, so you see the real code instead of `0xCC`.
- `set` writes a full 8-byte word with `PTRACE_POKEDATA`. Values are little-endian: `set addr 1337` writes `39 05 00 00 00 00 00 00`.

Try it on `test/vars`, which prints a global number and string:

```sh
nm test/vars | grep -wE 'secret|message|show'
./kdbg ./test/vars
kdbg> b 0x401136              # address of show()
kdbg> c
kdbg> x 0x404020              # secret (42 = 0x2a) followed by message
kdbg> set 0x404020 1337       # change secret
kdbg> c                       # the program now prints secret = 1337
```

## Signal handling

Harmless signals (`SIGWINCH`, `SIGCHLD`, `SIGALRM`, ...) are passed to the program silently, without stopping, like GDB does.


When the tracee receives a signal (e.g. `SIGSEGV`), the kernel stops it *before* delivering the signal and notifies the debugger. kdbg remembers that signal and passes it back on the next `continue`/`step` (the last argument of `PTRACE_CONT`), so the program behaves as it would without a debugger. `SIGTRAP` is never forwarded, since it is generated by our own breakpoints and single-steps.

```sh
./kdbg ./test/crash
kdbg> c        # stopped by signal 11 (Segmentation fault)
kdbg> r        # inspect the registers at the crash
kdbg> c        # signal delivered: process killed by signal 11
```

## How it works (M4)

The ELF parser lives in `src/elf.c`:

1. Read the whole file and check the magic bytes (`\x7fELF`) and the 64-bit class.
2. Walk the section header table (`e_shoff`, `e_shnum`) looking for `SHT_SYMTAB`.
3. Symbol names are not stored in the symbols: `st_name` is an offset into the string table, whose index is the symbol table's `sh_link`.
4. Keep defined `STT_FUNC` and `STT_OBJECT` symbols.
5. For PIE binaries (`ET_DYN`) addresses are relative to 0: the runtime load base is read from `/proc/<pid>/maps` and added to each symbol.

Stripped binaries have no `.symtab`, so only raw addresses work on them.

```sh
./kdbg ./test/vars         # also try ./test/vars_pie
kdbg> syms
kdbg> b show
kdbg> c                    # hit breakpoint 0 at 0x401126 <show>
kdbg> s                    # rip = 0x401127 <show+1>
kdbg> x secret 8
kdbg> set secret 1337
```

## How it works (M5)

- Disassembly uses [Capstone](https://www.capstone-engine.org/) (`cs_open`, `cs_disasm`) in x86-64 mode with Intel syntax.
- x86 instructions are 1 to 15 bytes long, so kdbg reads `n * 15` bytes (the worst case) and lets Capstone decode as many instructions as it can.
- Breakpoint bytes (`0xCC`) are replaced with the original bytes before disassembling.
- After every `step` and breakpoint hit, the current instruction is shown; in `dis` output it is marked with `=>`.
- Direct `call`/`jmp` targets are annotated with the symbol name when known.

```sh
./kdbg ./test/vars
kdbg> dis main 6           # see the two calls to show()
kdbg> b show
kdbg> c                    # => 0x401126 <show>: push rbp
kdbg> s                    # => 0x401127 <show+1>: mov rbp, rsp
```

## How it works (M6)

- `kdbg -p <pid>` calls `PTRACE_ATTACH`, which stops the process with `SIGSTOP`. That stop is ours, so it is not forwarded on the next `continue`.
- Symbols are loaded from `/proc/<pid>/exe`, the executable of the running process.
- On `quit` (or Ctrl+D) every breakpoint byte is restored and the process is released with `PTRACE_DETACH`: it keeps running as if nothing happened.
- On most distributions `ptrace_scope` is `1`, which only lets a process trace its own children. Attaching to an unrelated process then requires `sudo`.

```sh
./test/sleeper &           # prints a tick every second
sudo ./kdbg -p $!
kdbg> b tick
kdbg> c
kdbg> set counter 1000
kdbg> q                    # detach: sleeper continues from tick 1001
```

## How it works (M7)

With frame pointers, every function starts with `push rbp; mov rbp, rsp`, so each stack frame contains:

```
[rbp + 8]  return address   -> where the caller continues
[rbp]      saved rbp        -> the caller's frame
```

`bt` follows the chain of saved `rbp` values up to `main`. When stopped inside the prologue (e.g. right after `b func`), `rbp` still belongs to the caller, so the return address is read from `[rsp]` or `[rsp + 8]` instead.

Limitations: code compiled with `-fomit-frame-pointer` (common in optimized builds and libc) breaks the chain. Real debuggers use the DWARF unwind information in `.eh_frame` instead.

```sh
./kdbg ./test/nested
kdbg> b level3
kdbg> c
kdbg> bt                   # level3 <- level2 <- level1 <- main
```

## How it works: next / finish

Both use a **temporary breakpoint**, removed as soon as it is reached:

- `next`: Capstone decodes the current instruction. If it is a `call`, a temporary breakpoint is placed on the instruction right after it (`rip + size`) and the tracee continues; otherwise it is a normal single-step.
- `finish`: the return address is found like frame `#1` of the backtrace (`[rsp]`, `[rsp + 8]` or `[rbp + 8]` depending on the prologue), a temporary breakpoint is placed there and the tracee continues. On return, `rax` holds the return value.

**Recursion:** with a recursive function the same return address is hit by deeper calls too. Those have a lower `rsp` (the stack grows down), so kdbg only stops when `rsp` is back at the expected level. If a user breakpoint is hit on the way, kdbg stops there, like GDB.

```sh
./kdbg ./test/recursive
kdbg> b fact
kdbg> c                    # repeat: fact(5), fact(4), fact(3)
kdbg> d 0                  # delete the breakpoint
kdbg> f                    # returned, rax = 6   (fact(3))
kdbg> f                    # returned, rax = 24  (fact(4))
```

## How it works: hardware watchpoints

Software breakpoints patch the code with `0xCC`; watchpoints use the CPU's **debug registers** instead, so memory is never modified:

| Register | Purpose |
|---|---|
| `DR0`–`DR3` | the addresses to watch (so at most 4 watchpoints) |
| `DR7` | control: per slot, enable bit (`L_i`), condition (`RW_i`: `01` write, `11` read/write) and size (`LEN_i`) |
| `DR6` | status: bits 0–3 say which slot fired |

- User space cannot access debug registers directly, so kdbg writes them through `PTRACE_POKEUSER` at `offsetof(struct user, u_debugreg[i])`.
- The address must be aligned to the watched size (a CPU requirement).
- Data watchpoints are *trap-like*: the CPU stops **after** the instruction that accessed memory, so `rip` points to the next instruction and the new value is already visible.
- The CPU never clears `DR6`, so kdbg resets it after each hit.

```sh
./kdbg ./test/watch
kdbg> watch balance
kdbg> c                    # watchpoint 0 hit: 100 -> 150, inside deposit()
kdbg> bt                   # who changed it?
kdbg> c                    # 150 -> 120, inside withdraw()
```

## How it works: syscall tracing

`PTRACE_SYSCALL` works like `PTRACE_CONT`, but the tracee also stops at every syscall **entry** and **exit**.

- `PTRACE_O_TRACESYSGOOD` makes these stops report `SIGTRAP | 0x80`, so they cannot be confused with breakpoints.
- x86-64 syscall ABI: number in `orig_rax`, arguments in `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9` (`r10` instead of `rcx`, because the `syscall` instruction overwrites `rcx`), return value in `rax`. Errors are returned as `-errno`.
- At the entry stop the kernel has already set `rax = -ENOSYS`: that is how entry and exit are told apart.
- The line is printed at the exit stop, when the return value is known; the arguments are still in their registers because `syscall` only clobbers `rcx`, `r11` and `rax`.
- Syscall names come from `src/syscalls.h`, generated from `<asm/unistd_64.h>`. String and buffer arguments are decoded for `write`, `openat`, `open`, `access`, `execve`, `unlink`.

```sh
./kdbg ./test/files
kdbg> strace               # every syscall, including the dynamic loader's
...
openat(-100, "/etc/hostname", 0x0) = 3
openat(-100, "/does/not/exist", 0x0) = -1 ENOENT (No such file or directory)

./kdbg ./test/files
kdbg> strace openat        # stop after the next openat
kdbg> bt                   # who called it?
```
